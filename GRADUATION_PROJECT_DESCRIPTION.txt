=== PROJECT TITLE ===

Intelligent Warehouse Management System (WMS) with ML-Powered Demand Forecasting

A full-stack, role-based web application for managing multi-location warehouse and branch inventory operations in real time, enhanced with an XGBoost machine learning model for demand prediction and smart restocking recommendations.


=== PROBLEM STATEMENT ===

• Small and mid-sized retail businesses with multiple branches and warehouses rely on manual processes (spreadsheets, phone calls, paper forms) to track inventory, process sales, handle stock transfers, and manage loans — leading to data loss, stock discrepancies, and delayed decisions.

• Traditional inventory systems lack role-specific dashboards, meaning warehouse staff, branch staff, and business owners all see the same interface, creating confusion and security risks with sensitive data like pricing and profit margins.

• Demand forecasting in existing systems is either absent or based on simple averages, causing overstocking of slow-moving items and stockouts of popular products — directly impacting revenue and customer satisfaction.


=== PROJECT OBJECTIVES ===

• Build a production-ready, role-based WMS supporting 3 distinct user roles (Owner, Warehouse Staff, Branch Staff) with dedicated dashboards, serving 5+ physical locations (2 warehouses, 3 branches) and managing 1,500+ product SKUs.

• Implement a complete inventory lifecycle — from product intake and batch tracking through inter-branch stock transfers, point-of-sale operations, loan management, returns processing, and inventory auditing — all within a single unified platform.

• Develop and integrate an ML-based demand forecasting system using XGBoost that outperforms the traditional Weighted Moving Average (WMA) baseline, providing data-driven restocking recommendations to reduce stockouts and overstock situations.


=== SYSTEM ARCHITECTURE ===

The system follows a modern client-server architecture with three main layers:

1. FRONTEND (Client Layer)
   - Single-Page Application (SPA) built with React 19 + Vite
   - Role-based routing: /owner/*, /warehouse/*, /branch/* — each with dedicated layouts
   - Three layout shells: OwnerLayout, WarehouseLayout, BranchLayout
   - 86 source files, 30,648 lines of JavaScript/JSX code
   - 10 custom React hooks for authentication, product search, navigation badges, etc.
   - Real-time UI updates via Supabase subscription listeners
   - Multi-language support: English, Russian, Uzbek (Latin), Uzbek (Cyrillic)

2. BACKEND (Database + Auth Layer)
   - Supabase (PostgreSQL) as the Backend-as-a-Service (BaaS)
   - Row Level Security (RLS) policies enforcing data access per user role
   - Google OAuth 2.0 authentication via Supabase Auth
   - Database tables: products, categories, locations, product_list, transactions, transaction_items, branch_requests, branch_request_items, inventory_corrections, and more
   - Stored procedures (RPCs) for atomic stock operations: add_stock, deduct_stock
   - Database triggers for batch processing and constraint enforcement

3. ML PREDICTION LAYER
   - Python FastAPI server (port 8787) serving the trained XGBoost model
   - Trained on 18-24 months of synthetic demand data across all product SKUs
   - REST API endpoints: /health, /predict, /predict/batch
   - Vectorized batch predictions: 1,500 products in ~3 seconds
   - Graceful fallback to WMA when ML server is offline

DATA FLOW:
   User Action → React Frontend → Supabase API (REST/Realtime) → PostgreSQL
   Forecasting: React → HTTP POST → FastAPI → XGBoost Model → Prediction Response
   Authentication: Google OAuth → Supabase Auth → JWT Token → Role-Based Access

=== CHALLENGES & RESOLUTIONS ===

CHALLENGE 1: Race Conditions in Stock Operations
   Problem: When multiple users simultaneously sell or transfer the same product, stock quantities could go negative or become inconsistent due to concurrent read-modify-write operations on the product_list table.
   Resolution: Implemented PostgreSQL stored procedures (RPCs) using SELECT ... FOR UPDATE row-level locking. The deduct_stock and add_stock functions execute as atomic database transactions, preventing concurrent modifications. Added a database constraint to reject any update that would result in negative stock quantities.

CHALLENGE 2: Scaling to 1,500+ Products with Supabase's 1,000-Row Limit
   Problem: Supabase's default API returns a maximum of 1,000 rows per query. Many views (product tables, audit reviews, inventory batches) needed to display all 1,500+ products, causing incomplete data rendering and broken features.
   Resolution: Built a custom fetchAll() utility function that automatically paginates through results using Supabase's .range() method. It fetches data in 1,000-row batches and concatenates results until all rows are retrieved. Applied this pattern consistently across 20+ queries throughout the application.

CHALLENGE 3: ML Model Performance with Large Batch Predictions
   Problem: The initial ML prediction API processed products one-by-one in a Python loop, creating a new pandas DataFrame and calling model.predict() for each of the 1,580 products. This took over 30 seconds and caused browser timeouts (NS_BINDING_ABORTED).
   Resolution: Refactored the batch endpoint to use vectorized prediction — building a single DataFrame for all products and calling model.predict() once. This reduced prediction time from 30+ seconds to ~3 seconds for 1,500 products (a 10x improvement). Also increased the frontend timeout and added an ignore-ref pattern to handle React StrictMode's double-rendering.

=== IMPACT ===

This WMS directly addresses operational inefficiencies at a real multi-branch retail business in Uzbekistan. By replacing manual spreadsheet-based tracking with a real-time digital system, it eliminates data entry errors, reduces stock discrepancies found during audits, and provides instant visibility into inventory levels across all 5 locations.

The role-based access control ensures that sensitive financial data (cost prices, profit margins, revenue) is visible only to the business owner, while warehouse and branch staff see only the operational data they need — improving both security and usability.

The ML-powered demand forecasting capability transforms restocking from a reactive process (ordering when stock runs out) into a proactive, data-driven strategy. By predicting next month's demand per product per location, the system helps the business reduce stockouts of popular items while avoiding capital tied up in overstocked slow-moving products.

The multi-language support (English, Russian, Uzbek Latin, Uzbek Cyrillic) makes the system accessible to all employees regardless of their language preference, which is critical in Uzbekistan's multilingual business environment.


=== LESSONS LEARNED ===

1. DATABASE DESIGN IS THE FOUNDATION
   Investing time in proper PostgreSQL schema design — with correct foreign keys, unique constraints, and Row Level Security policies — prevented countless bugs later. The atomic stored procedures for stock operations proved essential when multiple users operated concurrently. Lesson: always design your data model before writing a single line of frontend code.

2. PAGINATION AND SCALE MUST BE PLANNED FROM DAY ONE
   Supabase's 1,000-row API limit only became apparent when the product catalog grew beyond that threshold, breaking multiple features simultaneously. Building the fetchAll() pagination utility and retrofitting it across 20+ queries was time-consuming. Lesson: always design for the full data scale from the start, not just the development dataset.

3. ML MODEL INTEGRATION REQUIRES INFRASTRUCTURE THINKING
   Training a model in a Jupyter notebook is fundamentally different from deploying it in a production application. The .joblib format required a Python server, the batch prediction needed vectorization for performance, and React's StrictMode created unexpected double-rendering issues. Lesson: model deployment architecture should be planned alongside model training, not as an afterthought.
